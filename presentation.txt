1. EXECUTIVE SUMMARY & THREAT MODEL
--------------------------------------------------------------------------------
- PROBLEM SCENARIO:
  A company stores confidential financial records and sensitive documents in 
  cloud storage. The threat model assumes that storage access could be compromised 
  (e.g., leaked API credentials, compromised cloud bucket permissions, rogue 
  cloud admins).

- ARCHITECTURAL DEFENSE (Zero-Plaintext Storage):
  Files are encrypted in backend memory BEFORE upload to cloud storage. 
  Cloud storage only ever holds AES-256-GCM ciphertext (<filename>.enc). 
  Plaintext data and plaintext keys NEVER touch cloud disks.

[SLIDE 3: CRYPTOGRAPHIC ENCRYPTION WORKFLOW]
- Title: Upload & Envelope Encryption Process
- Talking Points:
  "When a user uploads a document:
   1. The backend requests a unique 256-bit Data Encryption Key (DEK) from KMS.
   2. The cryptographic engine generates a fresh 96-bit random Nonce.
   3. The file is encrypted in RAM using AES/GCM/NoPadding.
   4. The plaintext DEK is securely zeroed out of memory immediately.
   5. Only the ciphertext (<filename>.enc) is pushed to Supabase Storage.
   6. Only the wrapped (encrypted) DEK and GCM tag are saved in the database."

[SLIDE 4: WHY AES-GCM OVER AES-CBC?]
- Title: Cryptographic Evaluation: GCM vs CBC Mode
- Comparison Points:
  1. AEAD (Authenticated Encryption):
     - CBC only guarantees confidentiality; it requires a separate HMAC for integrity.
     - GCM provides simultaneous confidentiality and tamper-proofing via a 128-bit 
       Galois Authentication Tag.
  2. Padding Oracle Vulnerabilities:
     - CBC requires block padding (PKCS#5/7), making it vulnerable to Padding 
       Oracle attacks (e.g., POODLE, Lucky 13).
     - GCM operates as a counter/stream mode with NoPadding, completely immune 
       to padding attacks.
  3. Parallel Processing:
     - CBC encryption is strictly sequential (block N depends on block N-1).
     - GCM counter mode allows high-speed multi-core parallel computation.

[SLIDE 5: NONCE REQUIREMENTS & KEY MANAGEMENT STRATEGY]
- Title: Nonce Safety & Envelope Encryption with HSM/KMS
- Talking Points:
  "Two critical rules govern our cryptographic security:
   - 96-Bit Nonce (NIST SP 800-38D): Every encryption uses a cryptographically 
     unique 12-byte IV generated by SecureRandom. Reusing a nonce with the same 
     key would lead to catastrophic XOR keystream recovery and forgery.
   - Envelope Encryption: The master Key Encryption Key (KEK) is locked in a 
     Hardware Security Module (FIPS 140-2 Level 3). Plaintext keys are never 
     persisted anywhere."

   - Upload any confidential document (e.g., 1st_sem.pdf or kd.pdf).
   - Click "Upload & Encrypt".
   - Highlight: Encryption happens in RAM before cloud transmission.

   - Click the Details / Inspect icon next to the uploaded document.
   - Point out:
     * Original vs Encrypted File Size (Encrypted size = Original + 16 bytes).
     * 96-bit Nonce / IV (single-use cryptographically random).
     * 128-bit GCM Authentication Tag (tamper-detection checksum).
     * Key Reference: Envelope encryption (wrapped DEK).

3. VERIFY IN SUPABASE CLOUD STORAGE:
   - Open Supabase Dashboard -> Storage -> encrypted-backups bucket.
   - Show the file is stored as <filename>.enc (e.g. 1st_sem.pdf.enc).
   - Show that opening the file reveals only raw binary ciphertext.

4. RESTORE & INTEGRITY CHECK:
   - Return to web app and click "Restore".
   - The backend downloads ciphertext, verifies the 128-bit GCM tag, 
     decrypts with the unwrapped DEK, and delivers the original file.

4. TOP VIVA & EVALUATOR QUESTIONS & ANSWERS
--------------------------------------------------------------------------------
Q1: What happens if an attacker modifies 1 bit of the encrypted file in Supabase?
A1: Because we use AES-GCM (Authenticated Encryption), the calculated Galois MAC 
    tag will not match the stored 128-bit authentication tag. Java's Cipher engine 
    immediately throws an AEADBadTagException and aborts before any plaintext is 
    released. Tampering is mathematically detected and prevented.

Q2: Why did you choose AES-GCM instead of AES-CBC?
A2: AES-CBC only provides secrecy, not message authentication. To make CBC secure, 
    one must implement a separate Encrypt-then-MAC scheme with HMAC-SHA256, and 
    CBC remains susceptible to padding oracle attacks. AES-GCM solves both 
    confidentiality and authenticity in a single, high-performance, padding-free pass.

Q3: Why is the Nonce size strictly 96 bits for GCM?
A3: NIST SP 800-38D standardizes the 96-bit nonce because it maps directly to the 
    GCM initial counter block without needing an additional GHASH hash calculation, 
    providing maximum efficiency and zero collision probability during initialization.

Q4: Where are the secret encryption keys stored?
A4: We use Envelope Encryption. Plaintext Data Encryption Keys (DEKs) are NEVER 
    stored on disk or database; they exist only briefly in RAM during encryption 
    and are wiped using Arrays.fill(key, 0). The database only stores the DEK in 
    wrapped (encrypted) form, protected by a master Key Encryption Key (KEK) 
    managed by a Hardware Security Module (KMS).
